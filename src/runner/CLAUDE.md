### Implementing a RunnerPlugin (external, e.g., Feature 02)

```typescript
const myPlugin: RunnerPlugin = {
  stepTypes: ['my-step'],
  async *execute(payload: StepPayload): AsyncGenerator<RunnerEvent> {
    yield { type: 'output_chunk', content: 'working...' };
    yield { type: 'step_complete', result: 'done' };
  }
};
runner.registry.register('my-step', myPlugin);
```

Plugins MUST yield a terminal `step_complete` or `error` event. Callers are responsible for their own timeout if a plugin may hang.

## Error Handling

`SlashbotRunner.executeStep()` never throws. All failure modes yield an `ErrorEvent`:

| Failure | Code | When |
|---------|------|------|
| Zod parse fail | `INVALID_PAYLOAD` | Before plugin lookup |
| No plugin + no default | `NO_PLUGIN` | After parse success |
| Plugin throws/rejects | `PLUGIN_ERROR` | During `yield* plugin.execute()` |
| Init fail (future) | `INIT_ERROR` | Bootstrap failure |

`credentials` values MUST NOT appear in any error message or log (DI-6).

## Guard Rails

- **Do NOT** add kernel initialization (`SlashbotKernel`) to this module — it must remain a plain TS library with no DI/kernel dependency (ADR in spec: clarification Q2)
- **Do NOT** use any `Bun.*` APIs in `src/runner/` — they won't compile to Node.js CJS target
- **Do NOT** store credentials in module scope — pass through to plugin per-call only
- **Do NOT** add new top-level files to `src/runner/` without updating `index.ts` exports
- **Do NOT** import from `src/runner/` inside existing slashbot modules — this module is a standalone library; the dependency arrow is one-way (agent-service → runner, never core → runner)
