## Overview

Slashbot is built on a plugin architecture where every capability is a plugin. The plugin system provides registration, dependency resolution (topological sort), lifecycle management (init/destroy), and a contribution model where plugins register action tags, prompt sections, commands, context providers, event subscriptions, and sidebar items. Third-party plugins can be installed from GitHub URLs.

  getCommandContributions?(): CommandHandler[];

## Features

### Node-RED Lifecycle Management

> Added: 2026-02-15 | **Modified: 2026-02-24** | Source: specs/001-nodered-lifecycle/, specs/003-nodered-setup-skill/

#### Overview

Manages Node-RED as a child process with automatic startup, crash recovery, health monitoring, and graceful shutdown. Node-RED is auto-installed in `~/.slashbot/nodered/` if not present.

#### User Stories

1. **Automatic Startup (P1)**: Node-RED launches automatically when slashbot starts. Non-blocking init with background readiness polling. Sidebar shows "NR: Starting" → "NR: Running".
2. **Crash Recovery (P1)**: Detects unexpected exits, auto-restarts with exponential backoff (up to 3 retries). Transitions to Failed after exhausting retries.
3. **Manual Commands (P2)**: `/nodered start|stop|restart|status|config|logs` for admin control. Alias: `/nr`. Idempotent behavior.
4. **Graceful Shutdown (P2)**: SIGTERM → timeout → SIGKILL on slashbot exit. Configurable timeout (default 10s).
5. **Configuration (P3)**: Persistent config at `~/.slashbot/nodered.json` with defaults (port 1880, health check 30s, max 3 restarts).

#### Key Entities

- **NodeRedInstance**: 6-state machine (disabled, unavailable, stopped, starting, running, failed). Tracks PID, port, uptime, restart count.
- **NodeRedConfig**: Persistent settings — port, enabled, healthCheckInterval, shutdownTimeout, maxRestartAttempts, userDir, localhostOnly.
- **Lifecycle Events**: `nodered:ready`, `nodered:stopped`, `nodered:error`, `nodered:failed`.

#### Architecture

- **NodeRedManager** (`services/NodeRedManager.ts`): Core service. Spawns Node-RED via `Bun.spawn('node', ['red.js', '-s', 'settings.js'])`. Health checks via HTTP GET. Logs to RingBuffer + file.
- **RingBuffer** (`services/RingBuffer.ts`): Fixed-size circular buffer (200 lines) for in-memory log capture.
- **Settings Generator** (`services/settings.ts`): Generates Node-RED `settings.js` from config.
- **Plugin** (`index.ts`): Standard plugin scaffold with sidebar contribution (dynamic label), prompt contribution (priority 160), command registration.
- **DI**: Registered as `TYPES.NodeRedManager`.

#### Business Rules

- Auto-restart only triggers on crash, never after intentional `/nodered stop`.
- Stale process adoption: probes port on startup, adopts existing Node-RED if responsive.
- Installation and lifecycle management delegated to the `nodered-setup` bundled skill (see Node-RED Setup Skill section below).
- Plugin contains zero references to npm, npx, or package installation (FR-012).
- Config files created with mode 0600.
- Localhost-only binding by default.

### Flow Management API

> Added: 2026-02-17 | Source: specs/002-flow-management/

#### Overview

Extends the `feature.nodered` plugin with a FlowManager service for programmatic CRUD operations on Node-RED flows. Provides bot action tags, metadata storage, flow validation with missing-node detection, and lifecycle events for downstream features.

#### User Stories

1. **Create and Deploy a Flow (P1)**: Submit a flow definition with metadata; system validates, deploys to Node-RED, stores metadata, returns flow ID and HTTP endpoint URLs. Event `flow:created` emitted.
2. **List Active Flows (P1)**: Retrieve all deployed flows enriched with custom metadata (creator, description, tags). Node-RED is source of truth for flow existence.
3. **Delete a Flow (P1)**: Remove a flow by ID from Node-RED and metadata store. Event `flow:deleted` emitted for downstream features.
4. **Update an Existing Flow (P2)**: Modify a flow's definition or metadata in-place. Validates before applying. Event `flow:updated` emitted.
5. **Bot Action Tags (P2)**: `<nodered-flow-create>`, `<nodered-flow-list>`, `<nodered-flow-delete>`, `<nodered-flow-update>` map to FlowManager operations for use in bot conversations.

#### Key Entities

- **Flow**: Node-RED flow (tab) with `id`, `label`, `type: "tab"`, `nodes: Node[]`, `disabled`.
- **Flow Metadata**: Custom metadata stored in `~/.slashbot/nodered/flow-metadata.json` — `flowId`, `creator`, `createdAt`, `updatedAt`, `description`, `tags[]`, `mcp` flag.
- **Flow Event**: Lifecycle event with `flowId`, `operation`, `label`, `metadata`.

#### Architecture

- **FlowManager** (`services/FlowManager.ts`): Core CRUD service registered as `TYPES.FlowManager`. Uses Bun's native fetch for Node-RED Admin API calls. Serializes operations (single-writer model).
- **FlowValidator** (`services/FlowValidator.ts`): Pre-deploy validation — JSON structure, tab node presence, wiring integrity, missing-node detection via `GET /nodes`.
- **FlowMetadataStore** (`services/FlowMetadataStore.ts`): Async JSON file persistence with schema versioning (version field starting at 1).
- **Action Executors**: `FlowCreateExecutor`, `FlowListExecutor`, `FlowDeleteExecutor`, `FlowUpdateExecutor` — parse XML action tags and delegate to FlowManager.
- **Flow Parser** (`services/FlowParser.ts`): Parses and normalizes flow definitions, extracts HTTP endpoints from `http in` nodes.

#### Business Rules

- Waits for `nodered:ready` before accepting operations.
- FlowManager init failure does not crash the app; plugin continues with FlowManager disabled.
- Metadata reconciliation on list: Node-RED is source of truth; orphaned metadata entries are cleaned up.
- Missing-node detection runs pre-deploy; flows referencing uninstalled nodes are rejected.
- Action output is plain text; connector-specific formatting handled by connector layer.

### Node-RED Setup Skill

> Added: 2026-02-24 | Source: specs/003-nodered-setup-skill/

#### Overview

Extracts Node-RED installation and lifecycle management from plugin code into a **bundled skill** (`nodered-setup`) — a markdown-driven instruction set the bot executes autonomously. The nodered plugin becomes a thin availability monitor + event emitter. The skill loader is updated to resolve bundled skills from `src/plugins/skills/bundled/` instead of `<repo-root>/skills/`.

#### User Stories

1. **Autonomous Setup (P1)**: On first startup with no Node-RED installed, the bot autonomously invokes the `nodered-setup` skill to install and start Node-RED. No manual intervention or pre-installed npm required.
2. **Lifecycle via Skill (P1)**: Start, stop, restart, and crash recovery all route through the skill. No process management code in the plugin.
3. **Heartbeat Availability Detection (P1)**: Plugin continuously monitors Node-RED via HTTP heartbeat (GET `http://localhost:{port}/`). State changes trigger events and context provider updates.
4. **Skill Instructions (P2)**: Skill provides clear, platform-aware install steps: detect npm/bun, install if missing (bun fallback via curl), install Node-RED to `~/.slashbot/nodered/`, verify health.

#### Key Entities

- **NodeRedSetupSkill**: Bundled skill at `src/plugins/skills/bundled/nodered-setup/SKILL.md`. Stateless; contains instruction sections: install, start, stop, restart, verify, troubleshoot. Frontmatter declares `requires.bins: [node]`.
- **NodeRedAvailabilityState**: 7-state union — `running`, `stopped`, `starting`, `stopping`, `unavailable`, `setup-needed`, `failed`. `setup-needed` is a formal state (not a transient sub-case).
- **HeartbeatMonitor**: Plugin component probing the Node-RED HTTP endpoint periodically (default: 30s).

#### Architecture

- **Bundled Skill** (`src/plugins/skills/bundled/nodered-setup/SKILL.md`): Markdown + YAML frontmatter. Bot follows instructions; executes shell commands via bash plugin.
- **NodeRedManager** (refactored): Removes `ensureNodeRedInstalled()` and spawn logic. Retains: heartbeat, state machine, event emission, settings generation.
- **Setup Trigger** (dual mechanism):
  - Context provider (`nodered.context`) dynamically returns setup instruction when state is `setup-needed` — visible on every LLM turn.
  - One-shot automation job (via automation plugin's `once` trigger) for immediate autonomous invocation. Soft dependency: null-guards `getService('automation.service')`, silently degrades to context-provider-only if automation plugin absent.
- **Crash Recovery**: Same dual mechanism; up to 3 retries with exponential backoff.
- **Settings Generation**: `settings.js` generated eagerly during plugin `setup()` — always ready before skill invocation.

#### Lifecycle Events

| Event | When |
|-------|------|
| `nodered:ready` | Node-RED responding (startup or recovery) |
| `nodered:stopped` | Intentional stop |
| `nodered:error` | Heartbeat failure (triggers restart flow) |
| `nodered:failed` | All restart retries exhausted |
| `nodered:setup-needed` | No Node-RED detected at startup |

#### Sidebar Labels

`NR: Running` | `NR: Stopped` | `NR: Starting` | `NR: Failed` | `NR: Unavailable` | `NR: Setup Needed`

#### Business Rules

- Plugin startup is non-blocking; if Node-RED unavailable, slashbot starts normally within 5 seconds.
- Plugin adopts externally-started Node-RED if heartbeat finds it responding on startup.
- Plugin generates `settings.js` eagerly in `setup()` before any skill invocation.
- Skill is invocable by the bot (autonomously) and by the user via `/skill run nodered-setup`.
- Workspace skills take precedence over bundled skills if the user provides their own `nodered-setup`.
- Node-RED admin API binds to localhost only by default.

### MCP Bridge

> Added: 2026-02-26 | Source: specs/004-mcp-bridge/

#### Overview

Extends the `nodered` plugin with `McpBridgeService` — a service that auto-discovers Node-RED flows with HTTP endpoints and registers them as tools in the bot's tool registry. Flows become usable bot tools without any manual configuration. Tools are dynamically registered/unregistered as flows are created, updated, or deleted.

#### User Stories

1. **Auto-discovery of Deployed Flows (P1)**: When a new flow is deployed in Node-RED containing an HTTP endpoint or annotated for exposure, the system automatically registers it as a tool within 10 seconds — no manual configuration required.
2. **Bot Invokes a Flow-Based Tool (P1)**: The bot invokes any flow-registered tool by name (`nodered:<slug>`), passing parameters and receiving structured results, exactly like any other tool.
3. **Dynamic Tool Updates on Flow Changes (P2)**: When flows are modified or deleted, the tool registry is updated in real time. The bot always has an accurate view of available tools.
4. **System Prompt Refresh on Tool Changes (P2)**: When tools are added, updated, or removed, a prompt refresh event is emitted so the bot's next interaction reflects the current tool set.

#### Key Entities

- **Flow Tool Definition**: Node-RED flow exposed as a tool — tool name, description, parameter schema, target HTTP endpoint URL, HTTP method.
- **Flow Eligibility Criteria**: A flow is eligible if it has an HTTP-in node AND at least one exposure signal: `mcp: true` metadata annotation, `mcp-<name>` label naming convention, or simply having an HTTP-in node (which is sufficient on its own).
- **FlowMetadata.params**: `Record<string, ParamDescriptor>` where `ParamDescriptor = { type: 'string' | 'number' | 'boolean'; description?: string; required?: boolean }`. Flows without declared params use fallback schema `z.object({ input: z.string().optional() })`.
- **Tool ID Format**: `nodered:<slugified-label>` — distinct from management tools (`nodered.*`).

#### Architecture

- **McpBridgeService** (`src/plugins/nodered/services/McpBridgeService.ts`): Core service. Subscribes to EventBus events (`nodered:ready`, `flow:created`, `flow:updated`, `flow:deleted`). Injected with `PluginContext` (obtained from `createNodeRedPlugin()` `setup()` closure). No new plugin manifest.
- **Tool Name Slugification**: lowercase, replace non-alphanumeric chars with hyphens, collapse consecutive hyphens, trim. Max 64 chars after `nodered:` prefix.
- **Registry Extension**: `Registry<T>` extended with `delete(id: string)` method. `PluginContext` extended with `unregisterTool(id: string)`.
- **EventBus injection**: `context.getService('core.eventbus')` in `setup()` — same pattern as FlowManager.

#### Business Rules

- An HTTP-in node is always required for tool invocation; flows with `mcp: true` but no HTTP endpoint are skipped with a warning.
- Duplicate tool names are rejected with a warning; flow authors must rename conflicting flows (no auto-suffixing).
- On each `nodered:ready` event: full teardown (unregister all `nodered:*` flow tools) + full re-scan.
- During steady-state: `flow:updated` events use diff-based reconciliation (add new, remove deleted, upsert changed).
- A tool is "changed" when HTTP endpoint URL, HTTP method, `FlowMetadata.params`, or flow label differs.
- Default invocation timeout: 30 seconds. Flows may override via `FlowMetadata.timeout` (ms).
- HTTP method is read from the HTTP-in node's `method` field; defaults to GET if absent.
- `McpBridgeService` init failure MUST NOT crash the app; plugin continues without MCP tools.
- Prompt refresh event emitted after every tool registration or unregistration.

#### Performance Targets

| Metric | Target |
|--------|--------|
| Tool registration latency | < 10s after flow deployment |
| Tool invocation overhead | < 100ms (localhost calls) |
| Startup scan (≤50 flows) | < 5s from `nodered:ready` |

#### Error Handling

| Scenario | Behavior |
|----------|----------|
| Node-RED unreachable during invocation | Returns structured error; tool stays registered; auto-retry on next `nodered:ready` |
| Flow endpoint HTTP 4xx/5xx | Returns structured error with status code |
| Invocation timeout (30s default) | Returns timeout error result |
| Unparseable response | Returns raw response as text fallback |
| Tool name conflict | Warning logged; conflicting flow skipped |
| Bridge init failure | Warning logged; bridge disabled; plugin continues |
